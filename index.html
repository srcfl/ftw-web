Energyplan

A plan for the whole home.

When should the battery charge? What energy does the car need before departure? Energyplan weighs these needs together with electricity prices, tariffs, solar and household forecasts, battery state and efficiency.

Your needs shape the plan.

  • Set charging goals and departure times. The planner reports missing energy when a goal cannot fit.
  • Use solar and stored energy across the coming hours, within equipment and site limits.
  • Update the plan as readings and forecasts change. Keep forecast caution separate from hard battery limits.

Energyplan runs as a compiled local worker. It proposes a plan; FTW Core checks every proposal and keeps its own fallback. The worker never sends commands to hardware.

Are we in control?

See what the equipment actually did.

A command reply does not prove that power changed. FTW shows whether a controlled device follows FTW, is waiting, is limited or needs attention.

01 / REQUEST

What FTW asked for

Keep the target and the command result visible. Core checks each command against the current site and equipment limits.

02 / RESPONSE

What the device reports

Fresh readings show whether the device follows. Old or missing readings stay distinct from a measured response.

03 / CONFIRMATION

What a separate meter confirms

When independent measurements support it, Core confirms the physical change. The available proof depends on the device and its readings.

Core keeps safety and control on the box. Stale required site-meter data stops dispatch; an unavailable planner leaves Core's local fallback.

Get running

Install FTW 0.x stable.

2.x and 3.x will receive no further updates. Switch to the new 0.x line for current fixes and features. Do not install 3.x beta.

Old FTW on a Raspberry Pi? Use a second SD card. Keep the old card. Prepare the new one and swap cards before running install commands. Guided transfer of old settings and history is not ready.

Choose one path below. A refused native install is a stop point; do not try Docker next. Same-host Docker needs a planned switch with old Core stopped and MQTT preserved.

Architecture

One local system across mixed hardware.

FTW Core owns measurements, state, safety and device commands. Energyplan supplies forecasts and proposed plans through a defined contract. Both run on your own host. The implementation uses Go, Lua drivers and compiled Energyplan workers.

Build with it

New hardware should be a driver, not a fork.

FTW drivers are plain Lua files with capability-scoped access to Modbus, MQTT, HTTP, WebSocket and TCP. Edit a driver on the Pi and reload it without rebuilding the Go runtime.

  • Start from an existing inverter, meter or charger driver
  • Test with simulators and the same public host API
  • Share device needs and test evidence through an issue
  • Skip the driver for an EV charger that speaks OCPP

function driver_init(config)
  host.set_make("My Inverter")
  host.mqtt_subscribe(config.topic)
end

function driver_poll()
  local watts = read_power()
  host.emit("battery", {
    power_w = watts,
    soc = read_soc()
  })
  return 1000
end
